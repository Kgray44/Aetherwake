This is OFFLINE preparation for a small source-bound Test K context-efficiency pilot. It has no credential reader, network entry point or live provider launch. The current review application and user profiles are outside its scope.

The proposed later ceiling is four Responses calls: two new engineering fixtures, each evaluated with scoped context and a declared full-context control. Order is scoped/full, then full/scoped. Both arms keep `gpt-6-luna`, low reasoning, a 1,024-token output ceiling, a 12,288-byte complete request ceiling and a 30-second provider deadline. No retry, escalation, web tool, arbitrary code execution or extra model grader is included. Live dispatch remains gated on a separate Root authorization and immutable candidate check; it must use the existing native protected-credential/ResponsesTransport path. A byte budget is not a measured token count.

Both contexts use the real `compileMissionContext` and `canonicalMissionContextSource` over canonical notes in a fresh synthetic Core database. The scoped arm pins the implementation and retrieves the corresponding contract. The control pins all twelve authorized fixture notes. Objectives, criteria, constraints, model controls and grading remain identical. Full means the declared synthetic corpus; it is a counterfactual control, not historical Vela code or all user history.

`fixture-seal.json` pins the public fixtures, separate held-out inputs/results and the existing compiler bytes. The fixtures were created after compiler development; the compiler is not tuned on their scores. This makes them held out from this optimizer's development, without a claim about the model's training data. Expected cases never enter a context or request body. The runner revalidates current canonical source versions, scope, policy and sealed files before the claim, immediately after the host claim, before every dispatch and after every response before grading. Changed or revoked sources stop the attempt; a response cannot retain a verified grade under withdrawn authority.

`describePilotRun` produces the host-reviewable binding: fixed authorization ID, candidate/head tree, fixture seal, configuration ID/version, model and controls, exact ordered fixture pairs, deterministic request/execution IDs, request-body digests and context manifest/scope proofs. `createPilotRunner` requires both the transport and a `RunAuthority.claim(binding)` port. The trusted host must verify the approved candidate/current configuration and atomically persist consumption of the fixed authorization ID before returning `{authorizationId, claimId, bindingDigest}`. The consumed ID must remain unavailable after failure, restart, a recreated runner or a changed binding. There is no fallback authority or production durable/live adapter here. The local used flag is only a fast guard; it does not establish durability. Offline tests use a real SQLite approval/consumption transaction, close/reopen it, then refuse the same authorization from a recreated runner.

Returned provider, execution and request IDs must match the approved slot, and dispatch must be explicitly confirmed by the native transport. Mismatched, absent or nondispatched provenance cannot be graded or continued. This is a trust boundary: metadata validates the injected native host's receipt; it cannot independently prove a dishonest adapter made an HTTP request. No live-host implementation or actual-dispatch qualification is claimed by fake-port tests.

The proposed patch is JSON arithmetic-expression data, interpreted with fixed operators, bounded depth/nodes and finite numbers. The grader independently checks seventeen hidden behavioral cases. It cannot execute model JavaScript, imports, shell commands or filesystem writes. This is a narrow function-repair pilot, not representative verification of every engineering workload.
