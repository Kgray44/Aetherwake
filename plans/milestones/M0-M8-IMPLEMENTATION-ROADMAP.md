## Program rules and critical path

**Critical path:** M0 governance/decision inventory and repeatable demo harness → M1 credible interactive visual slice → M2 real Codex bridge proof → M3 durable resource/conversation kernel → M4 user-directed contextual action → M5 verified agent operations → M6 context/branch intelligence → M7 bounded initiative → M8 release. M1 renderer and M2 adapter research can proceed in parallel after M0 interfaces; no permanent shell/renderer choice until comparable evidence. M3 schema prototyping may start during M2, but provider-dependent architecture is not frozen before the real bridge proof. Every vertical slice must demonstrate user path, failure, permission, persistence as applicable, and evidence; attractive mock state is labeled simulation. AW-CON-002–003, 016–021, 031–035; proposed AW-ENG-015–026, 093–098.

Every gate distinguishes **implemented**, **locally verified**, **integrated**, **reviewed**, **owner accepted**, **released**. A merge or a green build is not acceptance. The product owner accepts product/experience and foundational ADRs; technical reviewers check tests, architecture, security and evidence. If an advisory charter changes or receives acceptance, reroute the affected milestone and update links/criteria before integration. Public fixtures use synthetic content; no real private chats, credentials or telemetry in Git. Each evidence packet identifies commit, test commands/results, environment/device, captures for motion, failures and deferrals.

## M0 — Foundations

**Visible outcome.** A contributor can open the repository, understand the intended Aerynth/Vela experience, run a small repeatable synthetic demo shell or fixture, see the planned first user journeys and know which decisions remain open. M0 is planning and experiment readiness, not a working product.

**Engineering deliverables.** Maintain a routed requirement map for four anchor journeys: open an ordinary chat; manipulate a visual workspace block; turn a conversation idea into a Codex branch; inspect real versus simulated activity. Establish typed contract drafts, ownership map, source-safe synthetic fixtures, benchmark protocol and acceptance evidence template. Record a technology comparison matrix and M1/M2 spike scripts or recipes without selecting a permanent stack. Track the V2 router CLI failure if still reproducible; its library API and canonical files provide a documented fallback. Work packages: T01–T04 in the [task plan](../tasks/NEXT-CYCLE-WORK-PACKAGES.md).

**Functional criteria.** Reviewer can trace each journey to Constitution and relevant charter IDs, see file ownership and an observable test path, and run the benchmark harness on a synthetic fixture. The roadmap, contracts, ADR queue and tasks resolve links and IDs. The ordinary-chat path has no task/project precondition. **Nonfunctional criteria.** Reproducible setup, synthetic/public-safe data, bounded local storage, clear advisory-versus-binding authority, no hidden credentials, and a written target-device/measurement plan. Exact numeric performance budgets are research outputs, not invented defaults.

**Dependencies/parallel work.** Constitution/registry and current `main` precede all M0 work. Governance trace and contracts can proceed in parallel with benchmark fixture design in separate files/worktrees; integration review reconciles meanings. **Verification.** Router V1 validation; V2 section/full retrieval through its library API while CLI issue persists; link/ID validation; static scan of public fixtures; dry run of a benchmark with environment capture. **Risks/questions.** Which target Windows GPU tiers, screen sizes and accessibility configurations? What is the first real provider auth path? Which charter drafts will receive owner decisions and when? **Deferred.** Product implementation, canonical database, actual provider sign-in, polished UI and real background activity. **Gate.** Owner reviews priority/user journeys and unresolved authority/technology list; tech lead confirms work packages are executable. This does not count as M1/M2 proof. AW-CON-006, 009–010, 016; proposed AW-ENG-015–020, 027–031, 125.

## M1 — Visual Experience Lab

**Visible outcome.** A user can enter an interactive Liquid Intelligence environment: Vela presence responds to focus; a resource block can be selected, dragged, expanded and returned; a workspace transition preserves object identity. Layered materials and restrained particles have purpose. Every synthetic agent event has an obvious simulation label and readable non-motion equivalent.

**Engineering deliverables.** Two comparable, packaged candidate shell/rendering prototypes where feasible (T05), a six-domain Motion Coordinator interface/transition scheduler (T06), material and accessibility tokens, representative Vela/block/command scene (T07), performance instrumentation and captured scenario (T08). A reduced-motion/legibility-first path, low-tier quality mode, pause/minimize policy, transition diagnostics and interruption handling must be designed early. Avoid putting resource identity or progress in animation state.

**Functional criteria.** Drag/resize/reparent can be interrupted or reversed without losing focus, selection or resource identity. A visual transition to a full view and back retains draft/content referent. A keyboard user can reach the same core actions; reduced motion communicates state without relying on particles. No effect implies real Codex work. **Nonfunctional criteria.** Measure frame time distribution, input latency, CPU/GPU/memory, idle/minimized cost, text contrast and effect fallback on named target devices. Set proposed budgets from those measurements, then repeat with equivalent scenes; do not accept screenshot-only or peak-FPS evidence.

**Dependencies/parallel work.** M0 journey/contract baseline. Shell/renderer comparisons and motion vocabulary can run in parallel; final Motion Coordinator implementation follows integration of measurement findings. M2 can develop the adapter in parallel against normalized event interfaces. **Verification.** Recorded real interaction video plus frame-time traces and device/OS details; automation for identity/focus/interruption; accessibility review; reviewer inspection of visual quality and simulation labels. **Risks/questions.** Cross-window seamless interpolation may be unavailable; provide honest handoff. Blur/particles may dominate low-end GPUs. Candidate stacks remain open until ADR evidence. **Deferred.** Production event stream, live Codex state, durable multi-window workspaces, full graph navigation and perfected cross-display morph. **Gate.** Owner experience review of actual interaction and a technical review of measured cost/fallbacks; ADR approval only after fair comparison. AW-CON-015–021, 026; proposed AW-LIQ-015–022, 043–050, AW-PLT platform budget requirements, AW-ENG-016, 021, 026.

## M2 — Real Codex Bridge

**Visible outcome.** From a thin, clearly marked integration surface, a user can create or resume a real supported Codex thread, send a turn, read streamed output, see an actual approval request, choose a decision, cancel/interruption where supported, and recover from disconnect or auth expiry. The surface distinguishes provider completion from verified task outcome. An ordinary chat entry remains available without formal task setup.

**Engineering deliverables.** Version-pinned App Server adapter and protocol fixture (T09), capability/auth discovery (T10), approval/cancel/recovery slice (T11), real-provider verification report (T12). Map provider thread to app conversation ID; persist minimal safe metadata and event provenance, excluding real chat content from the public repo. Record actual installed binary version, auth mode, account scope, consent, provider limits, model access evidence and failure behavior. Use the [official App Server/plan-sharing guidance](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server) as a research starting point, then validate runtime behavior. A model catalog listing alone is not proof of entitlement.

**Functional criteria.** One genuine turn yields observed stream data with source IDs and a terminal state; approval allow/deny effects match the actual provider request; interruption and restart display honest state; provider failure does not destroy app-owned drafts/resource IDs. Unsupported operations are unavailable or explicitly emulated. A user can have a direct Codex chat with no task. **Nonfunctional criteria.** Secrets remain in protected storage/process boundary; protocol inputs are validated; event ingestion handles duplicates/gaps; reconnection has a bounded strategy; no public test artifact contains credentials or private transcript.

**Dependencies/parallel work.** M0 contract draft; M1 visual event projection can be reused but M2 proof must stand without visual polish. Conversation IDs and event envelopes are required before integration. Auth and protocol spikes can be parallel until joined in a real consent/turn test. **Verification.** Contract tests for recorded synthetic protocol frames, plus a live private smoke on an authorized account; capture sanitized receipts, binary/protocol versions, denial, cancellation, disconnect and resume observations. No live provider test implies every account/model is supported. **Risks/questions.** Exact authentication/entitlement route, current protocol compatibility, account access, token refresh, provider rate/usage limit, and native fork support. **Deferred.** Full task orchestration, parity with official Codex desktop, accessing existing ChatGPT history, multi-provider production support. **Gate.** Technical/security review of real trace and authority boundaries; owner reviews user-facing limitations before declaring core execution architecture viable. AW-CON-002, 004–006, 031–034, 062–065; proposed AW-CEX-002–008, AW-ENG-022–026.

## M3 — Workspace Kernel

**Visible outcome.** User creates a project/workspace, opens an ordinary conversation and a note, places the same chat in two blocks, rearranges, closes/reopens, and recovers after app restart without duplicated resource identity or lost draft. Removing a placement visibly differs from deleting the resource.

**Engineering deliverables.** Chosen persistence engine after ADR; resource/relationship repository, conversation history and provider binding table, local search baseline, notes capture, layout versioning and migration/recovery; single-display fallback for saved layouts. **Functional criteria.** Create/move/reopen, archive/restore, two-view identity, conflict handling and task-free chat work after restart; provider offline leaves local data usable. **Nonfunctional criteria.** Atomic writes, interrupted migration recovery, bounded large-history rendering, backup/export and synthetic privacy-safe fixtures. **Dependencies/parallel.** M0 contracts and M2 capability truth; data model/index/search and UI placements can proceed separately behind stable refs. **Verification.** Kill/restart and migration tests, two-window revision conflict, search coverage disclosure, layout topology change, large-history profile. **Risks/questions.** Local versus synced ownership, retention/export/deletion policy, indexing engine. **Deferred.** Cross-device sync, automatic organization, multi-agent execution, full CIE. **Gate.** Data integrity/security review and owner journey acceptance; no acceptance from a passing migration alone. AW-CON-026–035, 057–060; proposed Charters 03, 04, 07, 13–15.

## M4 — Vela Interaction

**Visible outcome.** User selects a file/message/note, asks Vela for an action, sees the actual interpreted target set, previews consequential effects, approves when needed, and can inspect/undo supported mutations. Direct local commands and quick note capture remain fast without model calls.

**Engineering deliverables.** Typed selection and action plan, deterministic native command routing, Vela interpretation adapter, permission broker, reversible operation receipts, focus-safe contextual UI. **Functional criteria.** Selected child + “all files in folder” expands correctly; “only this” narrows; stale anchors/permissions revalidate; ambiguous destructive scope asks once; harmless navigation executes directly. **Nonfunctional criteria.** Keyboard, reduced-motion, accessible target count, no credential exposure, bounded latency for local commands. **Dependencies/parallel.** M3 resource model and M2 provider truth; selection UI and policy tests can run separately against shared contracts. **Verification.** Scenario matrix of expanded/narrowed/ambiguous targets, denial and undo, keyboard/assistive review, prompt-injection fixtures. **Risks/questions.** OS external selection permissions, conflict semantics, undo limitations. **Deferred.** Voice, autonomous bulk reorganization, unrestricted computer use. **Gate.** Security and owner interaction review on real affected resources. AW-CON-011–015, 022–025, 039; proposed Charters 01, 06, 14–15.

## M5 — Agent Operations

**Visible outcome.** User can create a task from a conversation, supervise a bounded Codex execution, see actual events/approvals, compare attempts and inspect verification evidence. The original chat remains usable, and task creation stays optional for plain conversation.

**Engineering deliverables.** Task/agent/run separation, dependency scheduler, worktree/execution environment mapping, event ingestion and Intelligence Stream, evidence states and explicit cancellation. **Functional criteria.** One real lifecycle with failed and retried attempt; delegation preserves actor/source; completion requires declared verification rather than a final agent message. **Nonfunctional criteria.** Bounded concurrency, resource limits, auditability, safe termination, no false reasoning/progress. **Dependencies/parallel.** M2 adapter, M3 persistence, M4 trust; stream projection and scheduler can develop separately with event contracts. **Verification.** Real provider run with synthetic repo, approval/denial, duplicate/dropped event, failed test, retry and reviewer packet. **Risks/questions.** Worktree collisions, shared live service coordination, provider child-agent capability. **Deferred.** Arbitrary autonomous agent swarms, predictive scheduling. **Gate.** Technical/security review and owner acceptance of honest supervision. AW-CON-042–046, 061–065; proposed Charters 05, 09, 12, 14–16.

## M6 — Context and Memory

**Visible outcome.** User forks an ordinary idea into Codex and returns to ordinary discussion with cited results. Connected branches reveal selected post-fork knowledge; a user can accept or decline a handoff without transcripts being merged or source history being lost. Profiler displays only supported measurements.

**Engineering deliverables.** CIE retrieval/composition, source-preserving compaction, lineage/adoption workflow, cross-provider capability gating, token/latency profiler and replay coverage metadata. **Functional criteria.** Relevant retrieval with citation, denied branch sharing, stale source, independent branch edits, source retention/export and cross-provider fallback. **Nonfunctional criteria.** Relevance and cost regression set, privacy/redaction, latency budget measured on real data sizes, unavailable metric handling. **Dependencies/parallel.** M3 canonical history, M5 event evidence, M2 capabilities; retrieval benchmark and branch UX may run separately. **Verification.** Golden synthetic branch family, original-history hash, retrieval quality/cost comparison, provenance and access tests, replay gap test. **Risks/questions.** Handoff defaults and quality, provider context limits, semantic search drift, retention policy. **Deferred.** Full automatic global memory, assumed existing ChatGPT account history, unsupported provider-native forks. **Gate.** Owner approves sharing semantics and evidence of history preservation. AW-CON-031–035, 051–060; proposed Charters 04, 08–11, 14–15.

## M7 — Proactive Intelligence

**Visible outcome.** Vela notices an authorized meaningful change, proposes a useful action within attention settings, and lets the user inspect why, snooze or turn it off. Quiet/focus modes are respected; no policy silently grants new authority.

**Engineering deliverables.** Initiative policy engine, attention budget, schedule/monitor registration, adaptation record and revert, authorization-scoped event subscriptions. **Functional criteria.** Meaningful alert, false positive dismissal, quiet time, disconnected-monitor gap, reversible low-risk preference and explicit consent for high-impact action. **Nonfunctional criteria.** Bounded background CPU/network/token use, privacy-safe notifications and audit. **Dependencies/parallel.** M5 real events, M6 context, M4 policy; notification presentation can parallel policy engine. **Verification.** Synthetic time/event simulation plus real monitored scenario, user override and auth revocation tests. **Risks/questions.** What is meaningful enough to interrupt, and what retention is appropriate? **Deferred.** Unbounded background observation, silent privileged automation. **Gate.** Owner reviews interruption policy and real-use evidence. AW-CON-036–041, 062–065; proposed Charters 06, 14–15.

## M8 — Hardening and Release

**Visible outcome.** A versioned installable build preserves user data, restores across supported display changes, behaves accessibly and degrades clearly under provider failure; limitations are visible in release notes.

**Engineering deliverables.** Supported-platform matrix, installer/update/uninstall, signing or integrity verification, backup/migration/rollback procedure, security and dependency review, accessibility/performance regression suite, diagnostics and release evidence packet. **Functional criteria.** Representative complete journeys (ordinary chat; workspace/note; Codex execution; branch handoff; approval/denial; replay with gaps) pass on supported devices; failed update recovers; disconnected provider preserves local work. **Nonfunctional criteria.** Measured performance and idle behavior, reduced-motion and keyboard parity, privacy review, secret scan, accessibility review and vulnerability triage. **Dependencies/parallel.** M1–M7 accepted scope and ADRs; platform, security and documentation checks can parallelize, followed by integrated release candidate. **Verification.** Clean install/update/rollback on named devices, long-history and multi-display scenarios, artifact hash/signature, independent review and owner sign-off. **Risks/questions.** Distribution channel, code-signing identity, final support matrix and release cadence require decisions. **Deferred.** Unsupported platforms/providers and features honestly listed. **Gate.** Distinct engineering verification, security review, owner product acceptance and release authorization. AW-CON-015, 069–083; proposed AW-ENG-099–105, 121–125 and Charter 15.

## Cross-milestone acceptance packet

Each milestone packet records: source revision and branch; exact user journey and environment; functional tests with commands/results; motion captures/frame-time data when relevant; accessibility and reduced-motion checks; privacy/security checks; provider version/capability evidence when relevant; known failures, unavailable metrics, deferred features and owner/technical reviewer decisions. C-series Constitution and applicable D-series Charter 16 acceptance scenarios are mapped before owner sign-off. A draft document or task plan is preparatory evidence only. AW-CON-069–083; proposed AW-ENG-093–098, 106–110, 121–125.
