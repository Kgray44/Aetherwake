# Personal Context & Identity Engine — isolated core

This source-only module implements user-controlled personalization on an **injected existing canonical SQLite connection**. It opens no database, resource store, conversation backend, provider, network connection or native window. All committed examples/tests use fictional profiles.

`PersonalContextService` takes `db`, `transaction(work(db))`, optional `readTransaction(work(db))`, trusted `host`, native `crypto`, and optional `now`. Both transaction callbacks must pass the identical connection. The native adapter owns rollback, current account identity, local owner policy, actual canonical project/conversation scope resolution, protected storage location, key management and disclosure consent. The service does not accept permission booleans or credentials.

## Available operations

- `policy()/setPolicy({expectedVersion,patch})`: versioned storage, ordinary, Vela, sensitive and shared access settings. All default off. Storage permission is separate from provider disclosure.
- `importOriginal()/editImport()/readImport()`: exact pasted/export text, separate sections and immutable encrypted revisions. Edits preserve originals. Import creates **zero facts**.
- `reviewFact()/editFact()/correctFact()/readFact()`: individually user-reviewed knowledge/preferences with explicit uncertainty, category, keywords, source span and digest. Correction supersedes an old fact atomically; conflicting/unknown/inferred information retains that classification. No model/regex fact extractor or implicit conversation learning exists.
- `list({kind,after,limit})`: bounded owner-authorized metadata pages, including retained revoked objects; no body reads, even while encryption is unavailable. Historical body reads require access to the historical scope before decryption.
- `revoke()`: CAS revision, immediately invalidating old contexts. `hardDelete()` removes every encrypted revision and dependent fact/candidate-proof index, including old dependencies after a correction. Privacy deletion can be authorized by the host even when an old canonical scope is unavailable.
- `export({ids,maxBytes})`: explicit, bounded plaintext export returned in memory after per-revision authorization; no file writes. Selected exports can be pasted through `importOriginal(source:'user-export')`; approval is never restored automatically. A typed bulk round-trip restore UI is not implemented.
- `previewContext(request)`: deterministic relevance selection of whole approved facts and separately opted-in behavior. Returns exact item bodies, canonical scope proofs, request/policy binding, uncertainty/provenance, aggregate omission reasons, actual UTF-8 encoded bytes and digest. The original import/whole history is never automatically included.
- `validateContext(manifest,request)`: validates exact current versions/permissions/expiry/source digests/assistant/request/provider/policy and then requires trusted `context.disclose` authorization bound to the complete manifest digest. Returns the unchanged cloned manifest and the host-issued authorization reference. **Preview is not consent.** No reselection occurs here.

## Required integration boundary

The host's `resolveScope` must validate actual canonical IDs and current access/revisions, rather than merely accepting a well-formed ID. `authorize` must return an allow result with current policy version and an opaque native authorization reference, or deny. In particular, a renderer's requested shared IDs or `includeBehavior` is never sufficient authority. Native review must show the exact selected manifest/body before issuing the matching per-request grant; bind that digest into the actual provider request and validate again immediately before dispatch and before committing derived output. The module neither dispatches nor retries providers.

Ordinary behavior uses `assistant.ordinary`; Vela behavior uses `assistant.vela`. A behavioral import cannot be converted into shared knowledge or moved to another assistant by reviewing a fact. Shared knowledge additionally needs the shared policy, an explicit individual fact selection, relevance and host authorization. Project/conversation facts need exact matching current scope IDs. Provider consumers must serialize the returned `untrusted-personalization-data` **below their trusted operating/assistant instructions**, retain provenance/uncertainty, and never promote imported text into privileged instructions. No provider identity, conversation history, or Vela persona is defined here.

## Storage and bounds

Schema1 is additive to the same database (`personal_context_*` metadata tables). New initialization is idempotent; unknown schema/envelope versions fail closed without resetting data. There is no in-memory canonical state cache or in-flight record replacement on rollback. SQL CAS checks the actual current row; original/fact revisions are immutable. IDs, scope references, state and dependency IDs remain local metadata; private bodies, policy and source-content digests are encrypted. Encryption purpose and the encrypted envelope bind owner/object/kind/version; no key is stored in SQLite. Unavailable/failed crypto has no plaintext fallback. Native crypto integrity/key protection is an injected host obligation, not established by synthetic AES-GCM tests.

Bounds: 64 original sections, 4,096 facts per owner; 16,384 revisions and 16MiB ciphertext globally; 128 revisions per object; original text ≤256KiB encoded, fact text ≤4,096 UTF-16 units/16KiB encoded. A context examines ≤512 fact bodies (default128), plus the policy and at most one read of each of their distinct original sources, and includes ≤32 whole items/64KiB with explicit byte/item/scan omissions. Selection uses reviewed keyword-token overlap (behavior first when enabled), stable ID tie-breaking, and no semantic-model claims. A simple unrelated question receives no unrelated knowledge. Caller/provider prompt budgets may be smaller; the caller must allocate them explicitly. Export ≤128 selected objects/2MiB. Capacity rejects without truncation or eviction.

Hard deletion is **logical deletion from these live tables**, not guaranteed secure physical erasure of SQLite free pages/WAL, backups, filesystem snapshots, prior exports, or content already disclosed to a provider. Host retention/backup and privacy policy must describe those limits. It does not delete canonical conversations/resources.

## Evidence and remaining work

Tests exercise one real SQLite connection, AES-GCM with an ephemeral fixture key outside the database, exact imports, review, deterministic retrieval, native-grant denial, cross-assistant/source/scope fences, corrections, expiration, revocation, cascaded deletion, rollback and same-file restart. These are synthetic source tests, not native OS encryption, sign-in, provider inference, native UI/latency, behavioral fidelity or production acceptance.

Root integration still owns native OS encryption/key lifecycle, private storage/IPC/grants, import/review/settings UI, ordinary/Vela context wiring, provider prompt equality and live/native/behavioral/performance verification. Semantic indexing, automatic suggestions, canonical conversation-derived memory extraction, automatic profile migration and bulk export restoration are not implemented. No existing Vela/Core/App/provider behavior changes until that explicit integration.
