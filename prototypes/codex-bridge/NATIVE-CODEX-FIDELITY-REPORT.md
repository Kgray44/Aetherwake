# Native Codex fidelity audit — 2026-11-01

## Scope and authority

This report covers the isolated adapter in `prototypes/codex-bridge/`, stacked on draft PR #6 (`codex/04-codex-bridge`, commit `37004979657c8e74ffc7b2de0a461981c1870794`). The installed CLI and generated protocol bindings are both `codex-cli 0.153.3`. No production integration, visual prototype, workspace kernel, or governance files were changed. The Constitution is binding; the specialized charters in `governance/README.md` are published drafts pending owner acceptance. The V2 governance context command still fails with `Cannot read properties of undefined (reading 'some')`; the deterministic router and Constitution were read directly.

**Evidence vocabulary:** documented means an official protocol or configuration page describes an operation; discovered means the current host reported a value; enabled means the effective configuration permits it; authorized means an actual request succeeded under the current account and policy; live verified means an operation was observed against the installed backend. Fixture verified means a synthetic server exercised adapter semantics. A catalog entry is never an entitlement check. Unknown means the available evidence cannot decide. The machine-readable integration fixture is `fixtures/native-capabilities.json`.

The adapter deliberately leaves `baseInstructions` and `developerInstructions` unset unless its caller explicitly supplies them. Vela's future context must remain supplementary and scoped; repository content must never be promoted to privileged instructions. Aerynth conversation IDs must be stored separately from the native thread IDs returned here. No private thread contents, memory records, auth material, or local paths are committed.

## CLI versus bridge comparison harness

`npm run demo -- parity` starts two ephemeral turns with the same configured model, cwd, `read-only` sandbox, `never` approvals, and exact harmless input. One uses `codex exec --json`; the other uses the bridge/App Server. It compares terminal lifecycle and a fixed expected answer, not arbitrary wording. On this host the CLI emitted `thread.started`, `turn.started`, `item.completed`, `turn.completed` and exited 0; the bridge emitted a completed turn. Both returned the fixed answer. The bridge reported two instruction sources. CLI JSON did not expose its source list, so identical instruction loading was not directly proven by this comparison; the separate App Server instruction-source audit covers root and nested discovery. Neither turn used a tool, so tool parity remains open. This harness makes two model requests when run.

## Implementation notes and compatibility

- `NativeThreadSession` captures effective model/provider, effort, cwd, approval policy, ancestry, ephemeral state, and instruction sources. Existing `newThread`, `resumeThread`, and `forkThread` ID methods remain available.
- Thread, turn, and item pagination return validated page envelopes. App Server's omitted `sourceKinds` default excludes its own sessions, so the adapter explicitly requests all generated kinds unless a caller supplies a nonempty filter.
- `inspectEnvironment` projects only allowlisted config values and counts. It intentionally omits instruction text, MCP addresses, secrets, skill descriptions, and account identifiers.
- `adapterMethods` describes implemented wrappers, not discovered server support. The original `methods` field remains a deprecated compatibility alias. Unsupported RPCs remain explicit provider errors.
- Transport loss records an inferred gap for each known active turn. Terminal events retain native IDs and status. The 512-event ring is a diagnostic buffer only.
- Generated bindings live in `protocol-generated/` and are not hand-edited. To upgrade: install/select the target Codex CLI, record `codex --version`, generate into a **temporary** directory with `codex app-server generate-ts --out TEMP_PATH`, compare the generated tree and API signatures against the committed 0.153.3 bindings, then replace the generated tree in a separate scoped change only if needed. Run typecheck, fixtures, and live protocol probes against that exact installed version. Unknown response fields may be tolerated, but malformed fields used for safety/identity must fail closed or be explicitly marked unknown. Do not regenerate hundreds of files as part of this fidelity PR.
