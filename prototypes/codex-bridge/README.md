# Codex App Server bridge prototype

This is an isolated Node/TypeScript proof of concept for a future Aerynth provider adapter. It launches the installed Codex App Server over local stdio JSONL and keeps Codex thread IDs separate from any application-owned conversation ID. It does not create an Aerynth conversation store or product UI.

The wire parameter types in `protocol-generated/` were generated by `codex-cli 0.153.3` using `codex app-server generate-ts --out prototypes/codex-bridge/protocol-generated`. Regenerate them when upgrading Codex and re-run typecheck/tests. The runtime validates essential response IDs and shapes; generated TypeScript types alone do not validate untrusted JSON at runtime.

## Requirements and use

- Node 24 or newer, npm, and a Codex CLI supporting `app-server` on `PATH`.
- Existing Codex sign-in for the live command. This prototype does not create credentials or start a login flow.

```powershell
cd prototypes/codex-bridge
npm ci
npm run typecheck
npm test
npm run demo -- capabilities
npm run demo -- live
```

`capabilities` reads `account/read` and all `model/list` pages. Account output is limited to auth presence and account type. Catalog entries are **not** proof that a model is entitled or usable. `live` starts one thread with `read-only` sandbox and `never` approvals, sends one harmless fixed prompt, prints event metadata without message contents, and requires a provider `completed` event plus the exact answer. It makes one model request. Use `npm run demo -- inspect THREAD_ID TURN_ID` to read stored items without a new model request.

The adapter API covers thread start/resume/fork/read, turn start/interrupt, model/account discovery, and explicit reconnect/resume. It never automatically restarts the process. A caller can supply a server-request handler for decisions; without one, command/file approvals are declined. Other server requests fail closed as unsupported. A real application must expose each approval to the user with the proposed action and route the user's choice back through the handler. The fixture tests show decline and cancel; they do not prove safe acceptance of arbitrary commands.

The normalized `EventEnvelope` preserves provider method/payload, native thread/turn IDs, local receive time, provider turn timestamps when present, evidence class, sequence, and terminal status. It does not claim private reasoning or precise token usage. The in-memory event ring holds 512 events and reports its dropped count; it is not durable history. Persist full events behind an appropriate privacy/retention policy before using this in a product. `fixtures/example-events.jsonl` is entirely **synthetic**, with invented IDs and timestamps, and is safe to publish.

## Safety and failure behavior

- Stdio is local. No WebSocket listener is opened.
- Pending RPC requests, write bytes, and incoming line size are bounded. Timeouts reject requests. A process exit rejects active requests; a disconnected turn is unknown until reconciled, never marked successful.
- An explicit reconnect performs a fresh handshake and `thread/resume`, emitting a gap event. This cannot recover notifications lost during the disconnection. The caller must inspect stored thread/items and reconcile status.
- Missing executable, invalid request, auth absence, rate limit, model unavailability, crash, interruption, and approval decisions have fixture coverage. Actual provider errors can have more shapes than the fixture cases; unknown errors stay `rpc`.
- stdout/stderr from the child are not copied to public artifacts. The demo prints no account secrets, tokens, prompt contents, or raw events. Avoid storing live event payloads in this public repository.
