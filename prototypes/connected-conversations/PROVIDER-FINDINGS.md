# Provider capability, account access, and cost findings

Researched from current official OpenAI documentation on 2026-11-01. These are product integration findings, not a live account entitlement test. Model availability, limits, price, and eligible sign-in flows can change; a production adapter must discover them at runtime.

| Question | Finding | Design consequence |
|---|---|---|
| Can an app read a user's existing ChatGPT conversations after Sign in with ChatGPT? | No. Identity and optional plan-usage scopes do not grant conversation access. [Sign in quickstart](https://developers.openai.com/siwc/quickstart), [OpenAI cookbook](https://developers.openai.com/cookbook/articles/sign-in-with-chatgpt) | Existing ChatGPT history import/sync is **unavailable** in this prototype. Do not scrape account sessions or imply synchronization. |
| Can an eligible open-source/local app use a ChatGPT plan for AI requests? | Eligible Plus and Pro users can authorize plan usage through the documented Sign in with ChatGPT flow. Identity and plan usage are separate permissions; availability depends on app/account eligibility. [Quickstart](https://developers.openai.com/siwc/quickstart), [overview](https://developers.openai.com/siwc/token-sharing-open-source) | Treat it as an optional provider route requiring user consent and runtime capability checks. It is not implemented by the mock prototype. |
| Does a Plus/Pro login grant unlimited external API use? | No. Plan usage has account limits and errors; API Platform credits are a separate benefit for eligible Pro/Business subscriptions and linked organizations. API-key usage follows API billing. [Accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions), [API credits](https://developers.openai.com/api/docs/guides/chatgpt-api-credits), [Codex pricing](https://learn.chatgpt.com/docs/pricing) | Store usage category as included, metered, or unknown per route. Record quota windows/errors when discoverable. Never promise free or unlimited requests. |
| Is Codex always paid, or every ordinary request free? | Codex access spans Free and paid plans with differing limits, while API-key usage is metered. Eligible ChatGPT plan usage in outside apps is limited by the documented flow and account state. [Codex pricing](https://learn.chatgpt.com/docs/pricing), [Sign in quickstart](https://developers.openai.com/siwc/quickstart) | Do not infer cost from conversation kind. Cost belongs to the selected provider, auth route, model, and current usage state. |
| Does a model catalog prove entitlement? | No. Codex App Server's model/list may expose a bundled catalog; a completed inference turn is the access check for a specific model/request. [Codex App Server with plan usage](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server), [models and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference) | Distinguish model listed, available, authorized, and successful request. Refresh on account changes and handle late stream failure. |
| Can Codex natively fork? | Documented App Server thread/fork copies stored history through an optional lastTurnId, which is a turn boundary. [Codex App Server](https://learn.chatgpt.com/docs/app-server) | Only claim native fork when a live adapter verifies support and maps the selected source to a completed provider turn. Otherwise create an application-level continuation. |
| Does the Sign in with ChatGPT plan route keep persistent Responses conversations? | Current preview HTTP requests require store:false and stream:true and send the needed history in input. App Server can maintain local thread history and resume it. [Preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations) | Aerynth must own portable conversation records and preserve provider-specific continuity separately. |
| What confirms a successful AI turn? | A streamed Responses request must reach response.completed; errors may arrive after streaming begins. Codex App Server turn/completed must have completed status. [Models and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference), [Codex App Server with plan usage](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server) | Represent failed and interrupted handoffs and turns explicitly. Do not convert a partial stream into a successful artifact. |

## Capability contract used by the prototype

- Provider availability: available, requires authentication, disabled, unsupported, or unknown.
- Feature support, current authorization, and current availability are separate fields.
- Each model has availability, usage category, optional quota, and last error.
- Mock fixtures advertise only mock capabilities. Their "available" state means the deterministic local adapter works, not that any real account or model has been verified.

A production implementation should maintain capability snapshots with provider/version/environment/account scope, refresh on reconnect and auth changes, and record observed errors. It should avoid any account scraping, unsupported ChatGPT history access, or silent paid API invocation.
