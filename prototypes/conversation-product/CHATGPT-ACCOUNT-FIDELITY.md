Reviewed 2026-11-02 against application source `856f604af743031b69d858c05dfa409ce22566c7`, installed `codex-cli 0.153.3`, its freshly generated experimental public protocol, and the official sources below. This is a source/documentation investigation, not an authenticated account or desktop acceptance run.

**The requested native ChatGPT account fidelity is not established.** Sign in with ChatGPT (SIWC) supplies identity and separately authorized eligible inference; its documentation expressly excludes existing conversations and other account context. Responses inference must not be substituted for the native product. Existing ChatGPT history, Projects and account settings remain authoritative in ChatGPT. No local copy, invented memory, generic provider, or API-billed fallback was added. [SIWC overview](https://developers.openai.com/siwc/token-sharing-open-source)

The unified first-party desktop genuinely supports Chat, Work and Codex, with different histories and surfaces. That user-facing availability does not establish an API that Aerynth can call. [Use ChatGPT](https://learn.chatgpt.com/docs/use-chatgpt)

## Status interpretation

- **Supported:** the cited interface supports the stated, limited operation; actual integration/acceptance may still be pending.
- **Unsupported:** an explicit restriction of the named reviewed interface. This does not assert that every possible OpenAI partnership or future interface is impossible.
- **Unverified:** no qualifying public interface was established by this review. Absence from these sources is not proof of universal nonexistence.
- **RequiresAdditionalAuthorization:** the interface is documented, but eligibility, user/account/workspace consent and runtime access have not been exercised here.

## Implemented navigation seam

New browser-safe `src/first-party-interop.ts` uses the existing `ResourceSubjectRef` validator. `createFirstPartyChatInterop(host).open(subject)` is called only by an explicit user Open action. It resolves a current canonical binding through `host.resolveLocalCodexThread`, rejects local/legacy/other providers and unverified installations, and prepares only an existing local technical-thread route. It never reads transcripts, another app's storage or credentials.

The root-owned `host.requestOpen(target)` must revalidate canonical access, current provider/binding and same-local installation, then apply the native external-open allowlist. The target is untrusted data, not a grant. It must not be exposed as a renderer-provided authorization or enable arbitrary URLs. Its receipt is `requested`, `unavailable` or `unknown`; none proves a successful window open or turn. Root owns the actual native wiring and user action. This release does not launch the target app.

The original fidelity release made no Core/Main/App/OAuth changes and introduced no second resource/history database, account context cache or automatic context transfer. The owner's subsequent addendum explicitly authorized the separate ordinary inference route; the implementation hold is lifted. Native account-history, memory and synchronization parity remain unestablished.
