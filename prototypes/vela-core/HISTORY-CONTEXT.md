# Canonical conversation continuity: source release

This module supports bounded, explicitly reviewed provider history. Production enablement and native consent transport remain Core-owned; these checks invoke no actual provider or native UI.

`VelaService.previewProviderContext(resourceIds, {includeHistory, fits})` is read-only. It does not open Vela, create messages, or call a provider. Disabled history never calls the history projections. An absent conversation, legacy/unknown origin, changed scope, denied source, invalid proof or insufficient capacity yields no history or fewer complete recent pairs, with host-only omission reasons. `fits` must build the entire actual semantic prompt; the 16,384-byte execution ceiling is unchanged. Whole messages are never truncated or summarized.

The same canonical connection supplies bounded message headers, exact message bodies, current revisions, permission decisions and actual provider evidence through `VelaServiceOptions.history`. Each full read receives its remaining byte budget. Bounds are 12 lookback headers, four selected messages, 4,096 encoded history bytes, 64 flattened dependencies and 131,072 validation bytes. Current resource permissions and revisions are checked before reading derived message bodies. Both explicit source dependencies and upstream message/source dependencies remain transitive.

`PrivateFrozenProviderContext` is an in-process bridge constructed only by Core from its stored approved preview and consumed matching native grant. Service clones the reviewed context and fence, then validates before append, before provider dispatch and before the atomic response commit. `onAcceptedAppend` records the actual canonical request/input message ID, accepted body digest and exact sole R→R+1 revision. Other appends, scope/policy changes and source changes remain stale. Dispatch uses the frozen window; it never reselects after appending the initiating user message.

`validateProviderHistory(..., {metadataOnly:true, acceptedAppend})` is the schema-tool gate. It has no message bodies/history payload argument in its underlying verifier and performs no source/message body reads. It validates the current canonical revision, origin, flattened resource permission/revision, request proof metadata and native contribution evidence. Full gates additionally hash actual bodies before dispatch and response. The metadata gate relies on canonical revisions for legitimate changes; it does not pretend to detect an unsafe revisionless database body overwrite.

Schema 3 adds request origin, canonical input ID/digest, flattened provenance and history references/digests only. Selected history bodies are never copied into request context/state. Canonical reply append and response digest/pointer persist atomically. Versions 1 and 2 retain existing IDs, messages, requests and fingerprints exactly; missing historical origin/proof is not inferred. Unknown versions fail closed. Pending work restarts as unknown and is never replayed automatically. Unsent composer drafts are not history sources.

One shared `VELA_PLANNING_INSTRUCTION` export is used for semantic preview and dispatch. Internal request/conversation correlation IDs remain private canonical provenance; resource and selected history/message IDs remain explicit in egress. Host-only native review must show the exact built semantic prompt/history and omission reasons before issuing the grant. Those bodies, fences and callbacks must stay outside renderer preview/RPC state. Catalog tools must use only the metadata gate.

Executed source evidence: 94 Vela tests, including 15 proof-selector/metadata tests and 10 service SQLite lifecycle tests; strict Vela and backend typechecks. The synthetic canonical service plus actual formatter measured a 31-byte selected source with project/workspace metadata: full-catalog base 15,141 bytes, one whole pair 15,827 bytes (675 history bytes), older pair omitted for prompt capacity; discovered-catalog base 6,463 bytes, two whole pairs 7,744 bytes (1,270 history bytes). Provider calls during preview: zero. These fixture/provider-port checks do not establish native permission-dialog or live-model acceptance.
