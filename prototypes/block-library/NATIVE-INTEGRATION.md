# Universal block library integration

This increment extends the existing module and canonical adapter. It does not replace the workspace engine, conversation service, native authorization boundary, material renderer, or Motion Coordinator.

## Native port release

Forward the following `TemplateService` methods through the existing validated native command boundary:

| Method                          | Input                                       | Result                         |
| ------------------------------- | ------------------------------------------- | ------------------------------ |
| `findResources`                 | `ResourceDiscoveryInput`                    | `ResourceDiscoveryPage`        |
| `attachBlock`                   | `AttachBlockInput`                          | `CreatedBlock`                 |
| `preferences`                   | none                                        | `LibraryPreferences`           |
| `setFavorite`                   | kind, favorite, expectedVersion             | `LibraryPreferences`           |
| `getBlockSettings`              | placementId                                 | `BlockInstanceSettings`        |
| `configureBlock`                | placementId, expectedVersion, configuration | `BlockInstanceSettings`        |
| `previewWorkspaceFromResources` | `WorkspaceFromResourcesInput`               | `WorkspaceConstructionPreview` |
| `workspaceFromResources`        | `WorkspaceFromResourcesInput`               | `ConstructedWorkspace`         |

`createCanonicalTemplateHost` supplies discovery and placement authorization through its existing effective-grant callback. Search uses bounded keyset pages and returns only active resources of the selected kind owned by the target project or unassigned. Attachment rechecks resource and layout versions and grants in the canonical transaction, creates only a placement, and records a persistent command receipt. A disconnected execution provider does not prohibit reading or attaching an otherwise available conversation.

`createBlock` additionally accepts optional `configuration`. Existing callers remain valid. Template placement roles accept optional validated `configuration`; old schema-1 templates remain valid. Capture can take a third argument containing configurations keyed by placement ID. Supply `currentConfigurations` to the template mount to capture these preferences.

Schema 2 adds a singleton preference row and placement metadata in the same injected SQLite database, preserving schema-1 data. Settings are bounded to 16,384 historical placement IDs and contain only text scale and content presentation. They deliberately have no cascading placement foreign key: engine undo reconstructs placements by deleting/reinserting stable IDs. Detached settings remain recoverable for undo; they do not expose content or prevent canonical resource deletion. Access requires a currently authorized canonical placement and subject. Unsupported manifest versions remain stored and report an unavailable configuration state.

The integrated card now exposes unknown registered kinds, unsupported saved manifest versions, changed metadata bindings and missing resource references as explicit recoverable views. Its original editor subtree remains mounted and inert beneath that presentation, with value, selection and durable draft ownership retained. Unknown kinds cannot fall through to an editable generic note. Resource and subject cards share the same version-recovery state. An explicit Retry only rereads saved metadata; it performs no migration, replacement, deletion or provider action. Compatible recovery restores the existing editor subtree. Transient settings transport failures remain distinct from an unsupported type/version, and late reads for departed placements cannot repopulate the current workspace's failure state. CPU-only regressions exercise real canonical unknown-kind data, manifest version rejection and retained SQLite draft/settings/geometry; current combined native failure-state acceptance remains pending.

## Renderer integration

Mount `mountBlockLibrary` in the existing contextual Add surface and `mountWorkspaceTemplates` in New Workspace. Connect all released optional methods to expose attachment, favorites/recent use, and configuration. Older hosts show explicit unavailable states. Search includes names, categories, descriptions, resource kinds and controls. Previews are inert synthetic examples and never call a provider or read canonical resources.

In the existing block inspector mount `mountBlockConfiguration`. Apply saved/current preferences with `applyBlockConfiguration(article, configuration)` after decorating the existing article. It changes DOM presentation in place and retains textarea identity, selection and scroll. Import the module CSS once. Geometry continues through the workspace engine. The configuration module owns no animation timer or GPU context.

Template management includes duplicate, metadata/category editing, shape/geometry and organization editing, versioned update from the current workspace with explicit resource bindings, and archival removal. Editing/deleting a template does not rewrite an existing workspace. Preview and apply keep their existing access/version checks and canonical atomic behavior.

## Acceptance boundary

The native `workspaceFromResources` action accepts `{commandId,title,projectId,expectedProjectVersion?,resources:[{resourceId,expectedVersion}],organization?}`. The parent binds versions from the reviewed canonical plan; model text cannot supply effective grants. `previewWorkspaceFromResources` performs no writes. Execution revalidates inside the existing canonical transaction and invokes the same private placement pipeline as template application, with no transient fake template row. It returns `{createdWorkspaceId,resourceIds,placementIds,receipt:{commandId,operation,workspaceId}}`. Repeating an identical command returns that receipt; altered input conflicts. Resource IDs stay unchanged and no provider turn or task completion is inferred.

Template body schema 2 additionally supports explicit subject placements: `{subjectBinding:{mode:'reference',subject}}` or `{subjectBinding:{mode:'project-context',view:'project'|'resource-query',query?,kinds?}}`. Schema-1 resource-role templates remain supported. Capture requires an explicit subject-binding choice for each such placement. Context roles bind to the target project; a project overview requires a non-null project. The adapter's optional `authorizeSubject(subject,workspaceId?)` plus the engine's `allowSubjectAttachment` are required effective host grants. New library metadata schema 3 retains subject presentation settings by placement ID through undo/restart, with the same bounded retention as resource placement settings. Subject views create no resource row.

The focused suite covers the actual SQLite/kernel/engine/DesktopState adapter, attachment scope and identity, independent settings, undo/redo, schema upgrade and restart, and capability honesty. Type checking covers browser and native modules. These checks do not establish that the native host has wired the ports, that the visual design has owner acceptance, or that an actual Vela model interpreted a construction request. Combined desktop journeys, graphics recovery and renderer performance require the integrated host.

## Canonical subject experiences

The additive native methods are `subjectTargets(workspaceId)`, `createSubjectBlock(input)`, `projectOverview(projectId)` and `browseResources(input)`. Inputs/results are exported by `contracts.ts`. Expose capabilities under `LibraryCapabilities.subjects` for `project_overview`, `resource_browser` and `collection_browser` only after these paths are connected. Missing capability entries are unknown, never available. The optional `discoverBlocks()` service method returns all ten typed manifests with actual availability; `searchBlockCatalog` is the browser-safe equivalent.

`subjectTargets` returns up to 100 projects and 100 collections with `truncated`, filtered by the effective native subject grant. Global queries require an explicit grant. Placement rechecks the target workspace layout revision, subject type, active state and grants inside the existing canonical transaction. `createSubjectBlock` returns `{workspaceId,placementId,subject}` with no fabricated resource ID. Wire `mountBlockLibrary`'s `onSubjectCreated` to refresh the actual desktop and select that placement. Existing resource `onCreated` remains separate and unchanged.

Import `subject-view.css` and mount `mountSubjectExperience(element, subject, port, {active,openWorkspace,openResource,attachResource})` in the existing nonresource card body. The port has `projectOverview` and `browseResources`. The callbacks use normal canonical navigation/attachment commands and do not clone content. Set `active:false` for hidden/compact cards; call `setActive(true)` on expansion and `dispose()` on removal. Each refresh is demand driven, bounded and guarded against stale async responses; there is no polling or animation loop. For expanded cards call `refresh()` after relevant canonical changes. Browser queries search titles and IDs, not private note content or external files. Saved subject query/kind filters intersect with the current controls. Collection membership is read from the existing membership table. The placement count reflects authorized active workspaces, with an explicit completeness flag; an incomplete count is never classified as unplaced.

Project Overview reports actual registered resource counts, open/done task metadata, active workspaces and recorded local change events. It does not infer execution completion, progress percentages or live agent reasoning. Workspaces, resource-count scans, event windows and query pages are bounded and disclose partial results. Resource-query keyset pages scan at most 256 canonical candidates and return at most 100 rows. Each resource is reauthorized before return. No query causes a provider call, file crawl or data mutation.

Template limits are now 64 resource roles and 64 placements (the 64 KiB body bound remains). The source suite captures, previews and applies real workspaces with 0, 1, 3, 10, 25 and 50 distinct resources, proving reuse without new resource rows and exact Freeform geometry. This is functional source evidence; it does not establish renderer performance or native subject-view acceptance.

The desktop now loads each current placement's settings once into a bounded current-workspace cache, applies them in place with `applyBlockConfiguration`, and mounts `mountBlockConfiguration` in the existing Card inspector. Request failures are explicit and retryable through that inspector; unsupported versions are not reset. Removed placements release the renderer cache, preserving the canonical historical metadata for undo. Template capture supplies all current per-placement configurations and refuses to silently substitute defaults while any are loading/unavailable. These are renderer integration changes; native preference-change, editor-selection and restart proof remain required on the combined source.

`mountBlockLibrary` accepts optional `context: () => LibraryRecommendationContext | null`. The desktop supplies the actual current workspace project and visible canonical block kinds; the browser-safe `recommendBlocks` helper combines that metadata with runtime capability availability. These are explainable local rules, never inferred grants or fabricated intelligence. The Library's Recommended filter displays their reasons and excludes existing block types. It remains empty without context rather than assuming compatibility.

## Per-kind workspace views and shared inline chat

`identity-model.ts` reads only the existing canonical snapshot, authorized SubjectExperiencePort projection and allowlisted public event metadata. `identity-view.ts` mounts each kind's compact body and moves the existing Open/Back action into its header. No visual identity creates a canonical resource, grants access, fetches a URL, launches a provider or adds a renderer/frame loop. Browser pages include an optional canonical scope title only after the existing subject grant succeeds. Unavailable resources expose no retained body text; unsupported type/version recovery still preserves the original inert editor.

The desktop reports only presentation transitions (`setBlockPresentation`) from its existing Motion Coordinator paint pass. Visible subject cards read bounded four-row projections; opening a browser uses its existing full thirty-row page. Hidden cards invalidate late reads, retain the search text and do not poll. Resource/task/workspace actions retain real IDs and invoke the same existing controllers and versioned native commands.

`chat-view.ts` places `mountConversationChat` inside the existing block. The host supplies its canonical `ConversationDraftSession`, public ConversationProductPort and single conversationExecution adapter. The wrapper only suspends/resumes that observer and retains DOM identity; it does not render another transcript or own a composer store. Component flush/close persists drafts independently of pending provider turns. Resource sessions live through the native-window lifetime, including view departure while a Send is outstanding. The inline draft native helper now targets the shared `.cp-composer`, `.cp-draft-status` and explicit conflict controls; it remains unrun on this source.

CPU component regressions cover per-kind projections, real-ID actions, partial counts, unavailable data, stable search/caret/checkbox nodes, failed mutation recovery, header relocation with unsupported settings, hidden/denied/stale subject reads, shared-chat pause/resume and pending-send departure with later draft edits. The visual owner closed two source review findings (unavailable note/chat fallback and title-bearing peripheral accessible names) by read-only inspection. This is not native layout/visual qualification. The next parent-owned native slot must inspect normal/focused, narrow/short, large text, long title, empty/unavailable, chat selection/scroll and resize continuity; combined journeys A–F and the native scale matrix remain pending.

`ResourceDiscoveryInput` accepts optional `projectScope: 'compatible' | 'workspace-project' | 'unassigned'` and `collectionId`. Omission retains existing behavior. `LibraryCapabilities.discoveryFilters` separately advertises project/collection availability; absence is unknown, and the service/adapter reject requested disabled filters. The canonical adapter advertises its implemented filters while preserving explicit host disables. The adapter always applies the original target-workspace ownership fence before either filter; project scope cannot select another project's owner. Collection filtering requires its existing explicit subject grant, an active collection and an accessible owner project, then intersects actual canonical membership. Neither query mutates membership, changes ownership, creates a resource, or starts provider work. The current Library requests authorized collection metadata through its existing `subjectTargets` port only when Filter resources is opened; older hosts retain compatible search with an explicit unavailable collection-filter message. Actual-service component tests verify scoped results, exact-ID attachment and unchanged editor choices; denial clears old result actions. This follow-up has source/CPU evidence; native filter interaction remains pending integration acceptance.

## Related resources callback (App hookup pending)

`mountNoteExperience` accepts optional `openRelated(resourceId, anchor): void | Promise<void>`. Only supplied callbacks add Related resources to the existing document menu; opening it does not save, replace or dispose the note editor. `mountResourceLinks(root, resourceId, port)` from `resource-links-view.ts` returns `ready`, `refresh` and `dispose`. Import `resource-links-view.css` once in the host.

`ResourceLinksPort.read` returns current authorized `resources` and `relationships` from the canonical DesktopSnapshot. `change`, when supported, accepts only the existing graphAction `relate`/`unrelate` shape and returns its actual snapshot. Supply explicit `capabilities.relate`/`unrelate` booleans and optional canonical `openResource(id)` navigation. The host owns native policy, snapshot application and lifecycle; no new RPC family or relationship store is needed. Parent integration should use its existing graphAction broker, queue and surface manager.

The view shows incoming/outgoing direction, actual type and provenance. It projects metadata only, omits unavailable endpoints, bounds displayed links to 100 and candidate choices to 60, and provides local search. It can create references/depends_on/related_to links. Removal is limited to those three user-authored kinds; membership, ancestry and imported/inferred links remain inspectable but read-only here. A successful RPC alone is insufficient: its returned snapshot must show the requested effect with both endpoints still accessible. An unconfirmed action is never shown as saved or replayed; explicit Refresh is required before another mutation. Read failure clears stale controls, and late replies cannot remount a closed surface.

Six CPU regressions exercise the actual graphAction adapter, DesktopState, WorkspaceKernel and note menu component. They prove unchanged canonical IDs/content, direction/provenance, restricted removals, no false success/replay, denied/large results, closed-view lifetime and recovered draft/editor/selection retention. This callback remains unwired in the App and unrun natively, per the parent's frozen native candidate; no end-to-end Related resources claim is made.
