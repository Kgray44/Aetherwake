# Clock and timer domain

Persistent local domain foundation for semantic `clock_timer` resources. The service uses the owning `WorkspaceKernel` SQLite connection and synchronous transaction boundary. It creates no notes, workspace placements, provider calls, renderer state, notification windows, intervals, or timeout loop. The native host must register and expose the semantic resource kind and its block, command, RPC, and notification capabilities; these domain tests do not establish that integration or native UI acceptance.

## Integration API

Construct `new TimerService(kernel, host)` using `TimerHostPort` in `contracts.ts`. The host provides the exact same SQLite connection, synchronous `atomic`, semantic resource factory/read/version-touch, clock sample, and scoped event recording. Specialized resources use the kernel's existing canonical `resources.kind = 'generic'` identity, with the host returning semantic kind `clock_timer`, matching the established checklist pattern. Resource factory, body, canonical version, receipts, expiry outbox, and events must commit or roll back together. `recordEvent` must stage events transactionally; it must not publish externally before commit.

The synchronous service methods are `create`, `createWithOperations`, `read`, `mutate`, `list`, `nextWake`, and `reconcile`. `createWithOperations` binds resource creation and its initial operations to one command identity and transaction; changed initial operations conflict on replay. Renderer-facing `ClockTimerPort` is an asynchronous transport contract. `read` projects current time without writing; an elapsed running timer reports `due: true` until the host reconciles it. Each existing-resource mutation requires `commandId` and `expectedVersion`. Exact retries return the stored result after current write permission is rechecked; reused command IDs with changed content fail. Mutations address the canonical resource and timer IDs, so multiple workspace representations share state.

`TimerOperation` covers create/start/pause/resume/reset/extend/shorten/rename/cancel/delete timers, stopwatch start/pause/resume/reset/laps, IANA world-clock add/rename/remove, and expiry acknowledgement. Timers have independent run IDs and versions. Pausing holds remaining time; resuming continues the same run; reset starts a fresh ready run. Extending/shortening adjusts configured duration and current remaining duration together. Shortening a partially elapsed run to zero completes it. A ready duration must remain positive. Starting requires ready state, resuming requires paused state, and terminal timers require reset before starting again.

The host owns one scheduling loop. Re-arm it after committed mutations, permission/suspend/resume changes, and wake callbacks. `nextWake()` returns the earliest authorized writable timer request, capped at 60 seconds. Pass that request to `reconcile(resourceId, wake)`; resource ID, timer ID, run ID, timer version, and running state are rechecked. Obsolete callbacks perform no mutation. `reconcile(resourceId)` also repairs clock changes and startup recovery. The host should catch permission revocation and resource archival and stop scheduling that resource.

## Prepared native Vela apply

`../integrated-backend/src/timer-domain.mts` owns the native scheduling loop. Its `prepareCanonical(request, { signal, validate })` waits behind native startup/resume and already-queued reconciliation, snapshots the typed recipe, and returns a synchronous commit closure. Preparation does not open a host transaction, mutate canonical state, reconcile expiry, deliver notifications, or change the installed wake. Supported recipes create a resource with initial operations, mutate an existing resource, read a versioned document, list explicitly scoped documents, or read trusted current time in a valid time zone without creating a resource.

The host invokes that closure inside its existing canonical transaction together with the Vela host receipt. `validate` must synchronously recheck the host-issued grant, current policy, reviewed destructive scope, and other host authority. The closure rechecks cancellation/disposal/clock readiness and delegates canonical access, write permission, version CAS, and replay checks to the existing TimerService. Deleting a timer or removing a world clock remains review-required in the execution recipe; the host must enforce that review at the boundary.

Mutation results include the actual mutation receipt, the current canonical document, timer/world-clock/expiry IDs, and version postconditions. A historical replay may return a receipt older than the current document; `receiptMatchesCurrent` and the response helper disclose this. The pure `vela-timer-execution.mts` helper translates parser decisions to these recipes and derives response/focus only from actual returned canonical state.

The installed wake is preserved throughout synchronous apply. One coalesced microtask re-derives the wake from canonical state after the complete outer transaction commits or rolls back. This prevents a rollback from losing the old wake or leaking a newly computed expiry. That microtask does not reconcile or deliver; pending delivery uses the same native loop and its explicit delivery receipt/ACK contract. The default durable in-app notice is not an OS notification delivery receipt.

## Clock truth and expiry delivery

`TimerClockReading.monotonicMs` must come from a trusted elapsed clock that **includes suspended time**. Use a new `sessionId` whenever its origin is incomparable, including process restart unless the host proves continuity. A wall clock alone or a suspend-excluding clock does not satisfy this host contract. The service accepts fractional monotonic milliseconds.

Within one clock session elapsed time uses the monotonic clock. Forward/backward wall-clock changes are detected and deadlines are rebased during reconciliation. Across incomparable sessions, the durable wall anchor/deadline recovers remaining time; backward wall recovery cannot increase the stored remaining duration. This recovery is inherently uncertain and remains identified by `timing.wallRecovery` and each expiry's `wallRecovery` flag. The service does not claim exact elapsed time across a restart and simultaneous wall-clock change.

Expiry records are unique by timer ID and run ID and are created in the same transaction as completion. `pendingExpiries` returns up to 64 unacknowledged records per resource, including prior runs after reset or deletion, ordered by expiry time and ID. Acknowledge records using `acknowledgeExpiry`; repeat acknowledgement is safe. The host must use expiry IDs as delivery identities, recheck current access before notifying, and ACK according to its delivery policy. Database uniqueness prevents repeated expiry creation; external notification delivery still needs the host's idempotent delivery/acknowledgement handling. Resetting or deleting a timer does not silently acknowledge a prior expiry.

## Bounds and evidence

Bounds are explicit: 64 resources, 64 timers per resource, 128 stopwatch laps per resource, 16 world clocks per resource, 32 operations per transaction, 64 KiB per document, 8,192 command receipts and 8,192 expiry records in this installation. A configured duration is a positive integer of at most 365 days. Invalid values, incompatible schemas, unsupported transitions, capacity exhaustion, stale versions, and unavailable permissions fail closed. Acknowledged outbox rows and receipts are retained; no implicit history pruning is performed.

From this directory, run `npm test` and `npm run typecheck`. Type checking reuses the already-installed TypeScript and Node types in `../integrated-backend`; no dependency installation is required. The 19 SQLite-backed tests exercise disk reopen/recovery, command/version fences, transaction rollback, denial/revocation/isolation, shared canonical views, timer lifecycle, elapsed-clock/wall jumps, fractional clocks, stale wakes, duplicate expiry/ACK, stopwatch laps, world clocks, and capacity/input failures. The semantic fixture is explicitly synthetic and uses a real kernel/database; it does not claim actual desktop registry, OS suspend, UI, renderer, or notification verification.
