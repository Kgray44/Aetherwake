# Canonical Checklists

`ChecklistService` extends the application's existing Kernel/SQLite with checklist-domain data and bounded command receipts. Root's host creates a canonical `generic` resource and maps its logical kind to `checklist`; the service refuses a Note-backed or reused factory identity. Entries, groups and references have subordinate IDs, never agentic Task/resource identities. The module creates no workspaces, blocks, conversations, provider runs or event database.

Root supplies the synchronous `ChecklistHostPort` in `contracts.ts`: the identical connection/transaction boundary, canonical create/read/touch, current read/write authorization, authorized reference resolution, trusted actor/review attribution and existing Intelligence Stream recording. `touchResource` must call the released real generic-resource CAS mutation. A failed domain write or canonical event rolls back in the same transaction. Event payloads contain bounded operation IDs/types/counts and attribution classes, with no entry or conversation plaintext.

The async renderer interface is `application-contract/checklist.ts`. `create` has no workspace requirement and may explicitly link a canonical conversation resource. `mutate` accepts one canonical expected-version fence and ordered operations for manual entries, check/uncheck, descriptions, ordering, groups, priority, date-only due dates and source references. New items start unchecked. Checked state is classified only as manual or user-approved; provider completion, agent reports and verification are not inferred. Synchronization is currently manual.

Only real released reference resolvers may return available. Agent, full Task, Workflow and Timeline targets stay unavailable until their owning services exist. Revoked reference metadata is redacted from reads while its private stored link remains intact; independent manual edits still work. All mutations and retry receipts recheck current authorization.

Engineering bounds:256 documents,256 entries/document,32 groups,512KiB document JSON,1024 ID-only command receipts. These are implementation bounds, not binding product requirements or an OS quota. Unknown schemas fail without resetting retained data.

The source tests use Root's actual public generic creator/touch on the real Kernel/SQLite and its existing logical-kind table. They verify zero-workspace creation with zero Notes/placements, conversation references, edits/order/grouping/priority/dates/provenance, exact close/reopen continuity, CAS/idempotency, rollback, read-only/revocation and denied future-source gates. The event callback is a test boundary; Root owns real stream/IPC/native integration. These tests are not native usability, motion, provider or owner acceptance. Viewer/registry integration is a separate working increment; keep native capabilities unavailable until connected.
