# Canonical Checklists

`ChecklistService` extends the application's existing Kernel/SQLite with checklist-domain data and bounded command receipts. Root's host creates a canonical `generic` resource and maps its logical kind to `checklist`; the service refuses a Note-backed or reused factory identity. Entries, groups and references have subordinate IDs, never agentic Task/resource identities. The module creates no workspaces, blocks, conversations, provider runs or event database.

Root supplies the synchronous `ChecklistHostPort` in `contracts.ts`: the identical connection/transaction boundary, canonical create/read/touch, current read/write authorization, authorized reference resolution, trusted actor/review attribution and existing Intelligence Stream recording. `touchResource` must call the released real generic-resource CAS mutation. A failed domain write or canonical event rolls back in the same transaction. Event payloads contain bounded operation IDs/types/counts and attribution classes, with no entry or conversation plaintext.

The async renderer interface is `application-contract/checklist.ts`. `create` has no workspace requirement and may explicitly link a canonical conversation resource. `mutate` accepts one canonical expected-version fence and ordered operations for manual entries, check/uncheck, descriptions, ordering, groups, priority, date-only due dates and source references. New items start unchecked. Checked state is classified only as manual or user-approved; provider completion, agent reports and verification are not inferred. Synchronization is currently manual.

Only real released reference resolvers may return available. Agent, full Task, Workflow and Timeline targets stay unavailable until their owning services exist. Revoked reference metadata is redacted from reads while its private stored link remains intact; independent manual edits still work. All mutations and retry receipts recheck current authorization.

Engineering bounds:256 documents,256 entries/document,32 groups,512KiB document JSON,1024 ID-only command receipts. These are implementation bounds, not binding product requirements or an OS quota. Unknown schemas fail without resetting retained data.

The source tests use Root's actual public generic creator/touch on the real Kernel/SQLite and its existing logical-kind table. They verify zero-workspace creation with zero Notes/placements, conversation references, edits/order/grouping/priority/dates/provenance, exact close/reopen continuity, CAS/idempotency, rollback, read-only/revocation and denied future-source gates. The event callback is a test boundary; Root owns real stream/IPC/native integration. These tests are not native usability, motion, provider or owner acceptance. Keep native capabilities unavailable until connected.

## Retained viewer and Root integration

`mountChecklistExperience(root, canonicalResourceId, checklistPort, options)` is the same working component for a workspace content slot and independent direct focus. Import `view.css` with the other component styles. Supply a unique **presentation** `viewId` for each mounted view and the real borrowed `ExperienceMotionPort`; neither is a new canonical resource/block identity. Root's existing loop calls `frame()`, and the host calls `reflow()` after a surface resize. The component registers/removes only its own keys and creates no coordinator, scheduler, timer or CSS transition. All new controls have `data-aerynth-motion-control="true"` for Root's shared control feedback adapter. Closing surfaces/disclosures become inert immediately and hide when the borrowed pose settles. Hidden initial views do not read the service.

The viewer supports adding/editing entries, manual check/uncheck, full source-backed item order, groups, descriptions, priority/date fields, filters, source references and explicit group management. Local edits and retained editor nodes survive canonical refresh. Competing changes require explicit Use saved/Keep my edits before applying the local draft. `flush()` commits local item drafts before a host transition and refuses to pretend an unconfirmed save is resolved. An unsubmitted Add item form remains view-local; it is not silently committed as a new item.

Root injects `chooseReference()` and `openReference(ref)`; absence is shown as unavailable, with no raw-ID entry field, placeholder picker or navigation fallback. The service authorizes links again. The same referenced resource identity is used for navigation. Root owns reverse conversation/Related discovery through existing canonical relationships/indexes; checklist-domain references must not become a competing resource graph.

An acknowledged mutation followed by a failed refresh is reported as saved and blocks further edits until refresh. A lost/unknown acknowledgment retains its original command and retries that same durable receipt, preserving add/edit payloads without creating a duplicate entry. Source tests drive the actual service and existing MotionCoordinator through a finite host-owned test frame; they verify layout/disclosure/inert behavior, input/caret/draft continuity, conflict handling, source gates and both acknowledgment failure boundaries. No browser/native input or visual/performance acceptance is implied.

Root's existing `BlockKind`/manifest registration and actual Core/IPC/native capability gates are a separate integration boundary. Canonical checklist existence alone must not advertise a usable block. The current source viewer is ready for that registration; full desktop journeys, Vela reviewed additions, real source pickers, linked-conversation navigation, multi-workspace identity and native restart remain acceptance work.
