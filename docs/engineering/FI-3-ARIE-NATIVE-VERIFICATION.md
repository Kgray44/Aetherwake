## Ownership and rollback

`createMissionAdmission` remains the Platform Performance Governor entry point. Its `telemetry` and `inspectPolicy` methods expose local evidence to trusted host callers. `configurePolicy` and `rollbackPolicy` use a configuration revision check. `canLease` and `tryLease` enforce the current budgets. A fresh process has a fresh epoch and cannot reuse a prior live lease. A trusted embedder can supply a host preset through `NativeHostServices.resourcePolicy` on startup. A saved owner preference takes precedence over that preset.

The private policy view retains the latest effective transition in its current runtime epoch. It includes the transition revision and observation time, previous and current reasons, the coarse admission signals, and the number of new checkpoint requests by resource class. The native Performance menu shows the change and request count. A Windows smoke probe at 49.82% CPU changed from Balanced to Foreground/Gaming with a build lease active. The view recorded one build checkpoint request and three remote slots. The build reservation remained active until release. The smoke probe exercised lease accounting. The transition view records requests and does not certify task settlement. MissionService remains the owner of settlement evidence.

MissionService owns the queue, fairness, task attempts, timeout, cancellation, verification, and restart reconciliation. Its optional `resources.canAcquire/acquire` host seam uses the existing lane, executor ID, and canonical mission, task, and attempt IDs. It records `MissionAttempt.resourceLease` only for admitted attempts and releases reservations on actual settlement or failed journal admission. `MissionExecutionContext.resourceCheckpoint` is a cooperative request. Existing non-cooperative executors may finish and retain their reservation until settlement. The Core adapter classifies provider specialists as remote, restricted project checks as local build work, shipped-source inspection as CPU work, and bounded native observations as host I/O. Host I/O has its own budget and still observes the local memory floor. Existing authorization, provider lane and quota checks, storage reserve, and read-only runner isolation continue to apply.

The active policy exposes the prior effective budget, current reason, and revision. `previewAdjustment` accepts an expiring local-resource proposal bound to the current policy epoch and revision. It returns the prior and current budgets and the current reason alongside a bounded prediction. Increases and remote-budget changes require separate review. Duplicate evidence references, zero deltas, stale policies, expired proposals, and reductions that would leave all effective limits unchanged are rejected. A Windows smoke run at 29.92% native CPU utilization predicted a change from two CPU slots to one while live admission stayed at two CPU and three remote slots. The smoke run used a synthetic reference. The shared AEP contract defines the shape of findings. AEP owns resolution and authorization of current evidence and measurement of observed effects. Live advisory integration requires that resolver. If the Core integration needs to be rolled back, remove its resource hook and retain the existing admission callback. The additive optional attempt field requires no migration. Live reservations remain in memory.

## CPU worker isolation

The native shipped-source inspection uses a lazy, bounded Node worker pool under a CPU lease with a 64 MiB admission reservation. Its old-generation limit is 32 MiB. The reservation adds room for other V8 and native allocations. Three isolated Windows Node runs observed 18.98–19.29 MiB of incremental process RSS with one thread and 37.98–38.84 MiB with two. This is a planning estimate for the fixed inspection workload. The full process working set has no OS-enforced 64 MiB cap.

The worker accepts one fixed job with no path, command, or provider input. MissionService owns waiting and retries. The pool backpressures excess calls, retires idle threads when CPU or storage admission closes, and holds a retiring slot until thread exit. Tests verify that trimming leaves an active worker alone, a replacement can verify the same evidence, and the actual mission receipt records the reservation.
