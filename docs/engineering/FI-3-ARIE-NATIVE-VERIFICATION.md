## Ownership and rollback

`createMissionAdmission` remains the Platform Performance Governor entry point. Its `telemetry` and `inspectPolicy` methods expose local evidence to trusted host callers. `configurePolicy` and `rollbackPolicy` use a configuration revision check. `canLease` and `tryLease` enforce the current budgets. A fresh process has a fresh epoch and cannot reuse a prior live lease. A trusted embedder can supply a host preset through `NativeHostServices.resourcePolicy` on startup. A saved owner preference takes precedence over that preset.

MissionService owns the queue, fairness, task attempts, timeout, cancellation, verification, and restart reconciliation. Its optional `resources.canAcquire/acquire` host seam uses the existing lane, executor ID, and canonical mission, task, and attempt IDs. It records `MissionAttempt.resourceLease` only for admitted attempts and releases reservations on actual settlement or failed journal admission. `MissionExecutionContext.resourceCheckpoint` is a cooperative request. Existing non-cooperative executors may finish and retain their reservation until settlement. The Core adapter classifies provider specialists as remote, restricted project checks as local build work, shipped-source inspection as CPU work, and bounded native observations as host I/O. Host I/O has its own budget and still observes the local memory floor. Existing authorization, provider lane and quota checks, storage reserve, and read-only runner isolation continue to apply.

The active policy exposes the prior effective budget, current reason, and revision. `previewAdjustment` accepts an expiring AEP proposal bound to the current policy epoch and revision. It returns a bounded prediction for reductions without applying it and rejects any request to increase a limit. The focused test confirms unchanged policy and admission for valid previews, stale epochs, expired proposals, and mixed increase/reduction requests. AEP owns validation of the cited evidence and measurement of the observed effect. Live AEP calls, rejection-event publication, and experiments remain open. If the Core integration needs to be rolled back, remove its resource hook and retain the existing admission callback. The additive optional attempt field requires no migration. Live reservations remain in memory.

## CPU worker isolation

The native shipped-source inspection uses a lazy, bounded Node worker pool under a CPU lease with a 64 MiB admission reservation. Its old-generation limit is 32 MiB. The reservation adds room for other V8 and native allocations. Three isolated Windows Node runs observed 18.98–19.29 MiB of incremental process RSS with one thread and 37.98–38.84 MiB with two. This is a planning estimate for the fixed inspection workload. The full process working set has no OS-enforced 64 MiB cap.

The worker accepts one fixed job with no path, command, or provider input. MissionService owns waiting and retries. The pool backpressures excess calls, retires idle threads when CPU or storage admission closes, and holds a retiring slot until thread exit. Tests verify that trimming leaves an active worker alone, a replacement can verify the same evidence, and the actual mission receipt records the reservation. Crash tests exercise real thread exit and explicit submission to a replacement. The Core shuts the pool down after mission settlement.

Run `node prototypes/integrated-backend/src/mission-cpu-benchmark.mts` to compare inline inspection with one and two warm threads. On Windows with Node v24.18.0, each arm ran three measured batches of 24 inspections after one warm-up. Every digest matched. Medians reflect ambient host contention.
