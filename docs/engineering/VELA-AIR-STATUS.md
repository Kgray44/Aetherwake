Implementation source is the proposed [AIR specification](https://github.com/Kgray44/Aetherwake/blob/77ba4f8bd7f05e8c98b6e868e7bbda40ff2ea188/docs/specifications/VELA-ADAPTIVE-INTELLIGENCE-ROUTING.md), version 0.1.0. The Constitution and repository governance registry determine authority.

| Capability | Implementation and evidence boundary |
| --- | --- |
| Native and offline | The desktop Send broker tries the backend's Level 0 resolver first in Auto. It handles clock and date, physical RAM, bounded CPU and Windows GPU sampling, a bounded arithmetic parser, and workspace, project and execution status. Exact named workspace opening, resource lookup and opening, and named checklist creation use typed plans and receipts. A fresh Electron profile answered all ten local fact and calculator questions through the visible Send control on 2026-11-03. Both utilization counters returned measurements. The run recorded zero provider executions. With the primary RAM reader disabled in a separate probe, the installed read-only sandbox obtained valid physical memory counters without inference. If both paths fail, Vela reports the capability unavailable. |
| Local forecast | Plain local forecast questions can prepare the native weather action. The plan explains that the forecast sends rounded coordinates to the US National Weather Service. A test verifies that the plan requires review before dispatch and that unavailable native access stops the request without inference. Forecast parsing and rounded-coordinate transport tests use synthetic locations. |
| Quick and deep conversation | A connected ChatGPT-plan Responses adapter uses the signed-in catalog and supported model effort controls. Plain conversation uses a bounded conversational envelope without the app action catalog. The adapter checks connection, source and request authority before dispatch. Streaming Responses fixtures cover the wire model/effort, missing provider, unsupported pins, and stale authority. In an isolated profile, visible Vela Send answered a synthetic question using `gpt-6.1-terra` at `none`. A separate deep derivation used `gpt-6.1-sol` at `high` and returned the expected formula and reasoning. The provider reported 175 and 355 total tokens, respectively. |
| Agentic execution | The native review shows the working directory, model, effort, and read-only sandbox. The approved request reaches Codex's App Server thread and turn with its installed instructions. The live catalog supplies the default selectable model and its supported default effort. A live synthetic probe initially exposed an unsupported inherited model. After binding the catalog choice, one real Codex turn proposed the expected edit, Aerynth verified the reviewed write, and the installed read-only sandbox passed the selected Node test. A second live probe asked for a synthetic note in ordinary language. Codex chose the `search` action and Aerynth found the exact note. Both probes used the backend review boundary and separate synthetic data. |
| Reviewed repository edit | On Windows, choose up to four destinations in one checkout. Replace tracked UTF-8 files or use the native Save dialog to select one absent, untracked and unignored filename in an explicit creation request. The limits are 8 KiB per file and 10 KiB total for each set of before and after bytes. Read-only Codex receives approved relative paths and any approved existing bytes. A separate native review shows the before and after contents and hashes and identifies absent destinations. Aerynth checks Git HEAD, identities, approved bytes, and disk reserve before staging the batch. It publishes files individually and stops at the first failure. Replacements retain sibling backups. Creation refuses an existing destination. Recovery checks the original backup or recorded staged file identity alongside the new digest and supported JSON or JavaScript syntax. Windows tests use an isolated Git checkout and a Codex protocol double. They cover mixed creation and replacement, collisions, partial writes, and restart reconciliation without replay. |
| Project checks | A native picker and review approve up to four tracked Node tests, one tracked TypeScript configuration, or one tracked Node `.bench` script in one checkout. Standalone Send and checks after an applied edit use the same path. A ready Windows read-only Codex sandbox runs the exact arguments with networking disabled, a 20-second deadline, and zero inference. Output above 64 KiB or a timeout produces a limited result. The receipt retains the checkout HEAD, review digest and outcome without raw output. A benchmark script can report a sample count, median and 95th percentile in milliseconds. Vela attributes those numbers to the script. Reopening interrupted work shows an unknown result. A probe through the installed App Server passed ten tracked Node tests and the integrated backend's no-emit check. Earlier probes observed denied checkout and temporary writes. |
| Generated output | “Build this project” selects a tracked Node `.build` script and an absent destination in the same checkout. The read-only script returns up to 8 KiB of text on standard output. Aerynth validates supported syntax, stores the content digest, and offers a separate native review before saving the exact bytes. Collisions preserve the existing file. The installed App Server produced a 23-byte JSON file and a separate 12-sample benchmark in a synthetic checkout with zero model turns. |
| Composite and escalation | One reviewed request can send a native metric to read-only Codex. An explicit measure or selected-log request followed by analysis and inspection or editing can stage ChatGPT-plan analysis and a separately reviewed Codex handoff under one task ID. Declining the second review preserves the first answer. A live synthetic acceptance run checked the selected note, the exact handoff, a separately approved Codex edit and a separately approved 12-sample local benchmark. It recorded two real provider turns and verified one file write. The isolated harness supplied approvals after asserting the expected scope and content. For direct Codex log inspection and editing, the review includes the one selected log note and the selected files. Unpinned Auto can opt into one same-provider deeper attempt after a confirmed output-token limit. Partial output stays out of the retry. |
| Selected exchange handoff | From an eligible answer, **Continue with Codex** or **Continue with ChatGPT plan** prepares a reviewed follow-up to the other provider. It sends one whole selected exchange within the 4 KiB limit after revalidating source evidence, scope, dependencies, and conversation revision. All stages retain the local Vela conversation and share one task ID. Each stage has its own request and provider binding. An unconfirmed destination outcome stays unknown after restart. Bidirectional coverage uses provider doubles and the native broker. |
| Reconciliation | For an uncertain Codex inspection or file proposal with a retained thread and turn, **Check Codex outcome** reads the original terminal status in the original scope. It records observed status without replaying the turn or claiming verified work. The restart test preserves the exact provider outcome, including a successful provider turn with the original task still unverified. ChatGPT-plan requests use `store: false`. A disconnected turn without terminal evidence stays unknown and is never replayed automatically. |
| Settings and accounting | Vela resolves saved defaults in global, active project, workspace, Vela chat, selected agent profile and per-turn order. The Provider menu shows effective values and origins. The native review displays the selected agent version and instructions, and changing the agent invalidates the approval. One-send Auto clears inherited pins for that turn. Independent global and project limits cap total, ChatGPT-plan or Codex AIR attempts per UTC day. Each admitted stage counts once, including an unknown outcome. Local requests and capability probes use no attempt. A monetary cap fails closed when cost cannot be enforced. |
| Routing measurements | Off by default. Users can opt into observation, shadow comparison or adaptive ranking, with narrower per-project settings. The ranker compares confirmed models at the same supported effort and depth using recorded completion, explicit feedback, elapsed time and provider-reported tokens. It excludes simulated evidence and preserves pins and one-send Auto. The tests verify switching and rollback using seeded observations. The live comparison below establishes a latency improvement on the matched quick workload. |

## Matched quick-route comparison

An isolated signed-in test profile sent 12 synthetic questions to the static Auto baseline and an eligible alternative on 2026-11-03. Both used effort `none`. Model order alternated. The analyzer checked receipt IDs, completed provider state, returned model and usage against SQLite and took first-output timing from the recorded stream events.

| Model | Correct | Answer p50 | Answer p95 | First output p50 | First output p95 | Median reported tokens |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |

| `gpt-6-luna` | 12/12 | 2.561 s | 2.892 s | 2.319 s | 2.662 s | 174 |

The observations passed the production shadow eligibility rule when evaluated against the known answers. This was a small, single-host comparison of quick questions. Operational learning and user feedback settings stayed off throughout.

## Run the tests

- `node scripts/run-aerynth-acceptance.mts` runs the 16 application-domain suites. The Vela suite maps every action catalog ID to a plain-language request and checks routing, review and dispatch against a synthetic host. Other suites exercise the owning implementations, including real local SQLite and file operations.
- `node scripts/evaluate-vela-air.mts` checks fixed synthetic intent examples and records routing overhead. Its measurements cover intent classification.
- The development-only `--integration-vela-air-plan` harness uses a dedicated signed-in synthetic profile. Explicit `--air-plan-batch=1`, `--air-plan-batch=2`, and `--air-plan-batch=3` run the matched questions after a visible synthetic smoke turn. `--air-plan-mixed` runs the separately scoped mixed workflow. `node scripts/evaluate-vela-air-comparison.mts --profile=<absolute test profile>` verifies and compares the recorded batches without inference.
- `npm --prefix prototypes/visual-experience/cinematic-v3 run verify:application` passed the expanded desktop journey and same-profile restart on 2026-11-03. It verified persistence of workspace geometry, conversation ancestry, relationships, pins, bookmarks and camera state. The focused native Vela run used `--integration-vela --verify-air-local --verification-deadline-ms=85000` with a fresh absolute `--profile`. It verified ten local answers and the signed-out ChatGPT-plan alert, preserved the unsent draft and observed zero provider requests.
- `node scripts/verify-vela-air-codex.mts --run-one-synthetic-turn` explicitly exercises one live Codex proposal against a new synthetic checkout. The backend harness reviews exact scope, accepts only the known edit, and runs the chosen Node test in the installed sandbox. Normal automated tests do not use live inference.
- `node scripts/verify-vela-air-codex.mts --run-one-catalog-request` exercises one live search against a synthetic note. `--run-local-build-and-benchmark` exercises the installed local sandbox, RAM fallback, generated output and script-reported benchmark without inference.

Execution and verification claims are scoped to the supported Windows review operations listed above. Repository edits, generated output and local checks have fixed file, command and output limits. Verification records the selected check and its result. The 34 Vela action IDs have plain-language automated coverage against synthetic inputs. Live model-driven catalog selection was exercised separately for `search`.
