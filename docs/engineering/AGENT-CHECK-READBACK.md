# Exact-head check readback: read-only, not a publisher

`readExactHeadCheck` is the bounded readback component for a future isolated check publisher. It performs three GETs against the fixed GitHub API origin: current PR, the exact expected check ID, and the PR again. The calls share a 15-second transport deadline, reject redirects, and cap each response at 1 MiB while streaming. HTTP errors stop without retry. No POST/PATCH, workflow installation, key provisioning, settings changes, or live credential use is part of this increment.

The caller supplies the trusted GitHub-issued PR-target context, immutable verifier revision, expected GitHub App ID, exact check ID returned by its authorized publication, and out-of-band verification configuration. None may come from candidate artifacts. The module recomputes the expected sanitized check with `prepareExactHeadCheck` rather than trusting a supplied green report. It checks repository-bound API URL, check ID, App ID, contributor head, fixed name, completed state, conclusion and exact fixed output. A moved source or base commit, a changed target branch, or a closed PR observed on either PR read rejects the observation. A matching failure remains a failure observation; matching a check does not grant Task or owner acceptance.

This is not authentication for arbitrary JSON. The default HTTPS transport supplies the API read boundary only when run in a separately reviewed trusted runtime with an authorized read credential. Injected transport in tests is synthetic and establishes no real-provider trust. The caller must preserve trusted code/configuration, complete changed-path and tested-revision provenance, isolated artifacts and signing trust. No existing token is discovered or used by this change.

A readback is a point-in-time observation, not an atomic lock against later changes to a PR or check. The module neither selects a latest check nor resolves duplicate publications, does not attest workflow integrity, and cannot establish that branch protection requires the intended App. Idempotency, authorized check creation, final pre-publication identity check, App-bound enforcement, hosted positive/negative validation and real owner acceptance remain separate operational gates. Existing CI/native/security requirements stay in force.

API shape reference: https://docs.github.com/en/rest/checks/runs#get-a-check-run . Tests use only ephemeral fixture keys, fake credentials, local synthetic artifacts and synthetic HTTP responses. No live-provider validation is claimed.
