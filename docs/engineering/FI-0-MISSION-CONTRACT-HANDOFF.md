# FI-0 mission contract handoff

Program B contract slice based on `7747e8c723b5961d6edfd6fb75758a50e87e7ac6`. This change implements the versioned candidate boundary in the existing mission planner.

The [proposal module](../../prototypes/integrated-backend/src/mission-proposal.mts) exports `MISSION_PROPOSAL_CONTRACT`, `MissionProposal` and its provider schema. New planner requests ask for `aerynth.vela-mission-proposal@1`. The host rejects explicit unknown versions before compiling and still accepts the old unversioned shape through the closed field allowlist. The compiler resolves host catalog keys into the existing `MissionPlan`. MissionService validates the executable graph and binds accepted work to scope, request and plan revision in the existing `aerynth.vela-mission@1` record. A provider candidate cannot supply scope, an arbitrary executor, a native grant or a persisted mission record. The candidate marker stays outside the accepted plan and persisted schema.

The change affects the planner prompt and schema fingerprint. A previously issued planning offer must be refreshed at the current contract if its fingerprint changes. Existing mission IDs, source references, request digests, persisted data and native executor contracts require no migration. A rollback reads the same accepted mission records and resumes issuing the prior provider schema. Refresh an in-flight offer across the version change.

## AEP experiment and learning records

`aerynth.experience.experiment@1` binds a scoped experiment revision to distinct baseline and candidate policy references, cohort and holdout references, declared metrics and guardrails, and separate trace references for each arm. Evaluated records require both arms and evaluation references. Unavailable quality remains explicit. `aerynth.experience.finding@1` binds an advisory disposition to the exact evaluated experiment revision and project/workspace scope. A recommendation requires a benefit and a passed quality gate. Negative and inconclusive outcomes can retain the baseline.

Run `node --test prototypes/integrated-backend/tests/aep-experience-contract.test.mts` for round-trip, version, scope, evidence, and quality-gate checks. These decoders are the JSON boundary for the shared contract. Before supplying an experiment to the finding decoder, AEP must resolve its current revision, trace provenance, and independently recorded evaluation through existing owners. CIE must check current scope and source authorization before projecting any finding. An effective policy or authorization grant comes from AIR, MissionService, ARIE or the CIE policy owner through its existing review boundary. No storage migration is needed because this change introduces no persistent experiment table or automatic policy path.

## Current evaluation-reference consumer

The [evaluation reference contract](FI-0-EVALUATION-REFERENCE-CONTRACT.md) adds a closed, versioned Core read for exact native CPU/RAM verification receipts through MissionService. It resolves current mission/plan/task/attempt/evidence identity and source authorization, returns bodyless host-oracle provenance, and rejects unsupported evaluator namespaces. Its coverage is native task evidence only; independent experiment-wide quality remains explicitly not evaluated and no policy promotion is authorized. Existing experiment/finding decoders remain reference-only and require no schema migration. No retention default, export recipient or persistent experiment store changes.
