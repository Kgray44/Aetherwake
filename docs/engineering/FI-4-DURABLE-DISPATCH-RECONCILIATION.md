## Additive seam, recorded before implementation

`MissionAttempt.dispatch` is optional host-owned metadata: versioned contract, exact attempt ID, reserved/entered state and original started-event journal revision. Admission commits reserved; immediately before `executor.run`, MissionService must atomically compare the exact running attempt and reserved record, then commit entered. Old continuations cannot execute after recovery changes the attempt state. A crash after entered commits remains uncertain even if invocation might not have begun.

`MissionAttempt.reconciliation` is an optional versioned receipt for proven not-dispatched only: exact attempt ID, dispatch reservation revision, observed journal revision, timestamp and fixed MissionService dispatch-gate authority. It is committed with terminal state and the existing recovered/settled event in one canonical transaction. Receipt fields are not accepted from renderer/model/ordinary controls. No new table, event type, scheduler, FI-0 namespace or provider API is introduced. Existing records lacking the new versioned reservation cannot acquire this proof retroactively.

This is a gate inside the actual MissionService execution adapter, not a general callback accepting claims of quiescence. For a valid reserved record, state recovery plus the mandatory dispatch CAS proves the old executor continuation cannot enter. It does not prove anything about an executor that entered, remote provider liveness, process descendants or file writers. Such attempts retain their original uncertain fence. FI-0 CPU/RAM evaluation references never participate.

Consumers must preserve these fields as evidence without treating them as verified task success. A failed/cancelled no-dispatch task never automatically retries a non-replayable executor. General terminal readback requires separate qualified source adapters and a reviewed contract. Mixed old/new concurrent binaries are unsupported: an older binary can bypass this new entry gate. Deployment must stop old owners before enabling this recovery behavior; these cloud changes do not qualify rolling-version concurrency.
